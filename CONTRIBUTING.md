# Contributing

## Running it

```sh
cargo run -- examples/host/basic-widget
```

Every example brings the framework it requires, so install one before running
it:

```sh
cd examples/aether/timetracker && pesde install
```

Dew itself declares no framework. `cargo test --manifest-path host/Cargo.toml`
borrows one from an example that has installed it.

## The build identifier

`dew --version` (or `-V`) prints an identifier shaped like Cargo's own
version plus a running build count, for example:

```
0.1.0.242
```

The first three numbers are `host/Cargo.toml`'s version. The last is a
plain count of commits, incrementing on every commit regardless of what
changed. The same identifier appears in the tray's About entry and at the
top of a panic report, so a crash always carries it even when nobody
thought to ask for `dew --version` separately.

None of it is a compatibility promise. It does not say whether a given mod
still works after an update; that answer lives entirely in
`experimentalDatamodel`'s revision pinning (see
[docs/applet_contract.md](docs/applet_contract.md)), not in this number. A
build with a higher count is not guaranteed to behave the same as one with
a lower count, and a mod that needs that guarantee should pin the
revisions it depends on rather than reading this string.

## Checking it

```sh
lune run scripts/smoke.luau            every command the CLI promises
lune run scripts/verify_boundaries.luau  Dew owns its host outright
cargo test --manifest-path host/Cargo.toml
```

CI runs those, plus the build and the applet mounts on both Windows and Linux.

## Editor setup

`.vscode/` is gitignored, so this repository carries no shared editor
settings -- add these two entries to your own `.vscode/settings.json` for the
[luau-lsp](https://marketplace.visualstudio.com/items?itemName=JohnnyMorganz.luau-lsp)
extension to stop flagging real, working-at-runtime code as an error:

```json
{
  "luau-lsp.types.definitionFiles": ["types/dew.d.luau", "types/datamodel.d.luau"],
  "luau-lsp.types.roblox": true
}
```

`types/dew.d.luau` is what an applet is handed (`dew`, `Instance`, and
friends' shapes as a guest script sees them). `types/datamodel.d.luau` is
generated by `cargo run --bin generate-datamodel-types` (see that binary's
own header) and owns the entire DataModel class/enum hierarchy this host
accepts, `host/src/datamodel/extensions.rs`'s Dew-original rows
(`InputActionLabel.InputAction`, `GuiObject.BlendingMode`/`Enum.BlendMode`)
included. `luau-lsp.types.roblox: true` still has to stay on: it is what
supplies the value types (`Vector3`, `UDim2`, `Color3`, `CFrame`, and the
rest) `types/datamodel.d.luau` deliberately does not redeclare.

**The generated file has properties only -- no methods, no events.**
`rbx_reflection_database`, the one source `generate-datamodel-types` reads,
carries no method or event signatures for any class, and because Luau's
type-checker replaces rather than merges a same-named `declare extern type`
across definition files, every class this generator emits replaces Roblox's
own declaration outright. That means `instance:Clone()`,
`RunService.Heartbeat`, `GetPropertyChangedSignal`, and every other method or
event, now shows a real (if unwanted) editor error on classes this file
covers -- which is every class, since it owns the whole hierarchy. This is a
known, accepted tradeoff (see `generate_datamodel_types.rs`'s header for why
two narrower designs were tried first and both broke worse), not a bug to
chase down locally. `scripts/fetch_api_surface.luau`'s existing ~40-class
vendored method/event subset is the incremental path to closing it further.

The same "replace, not merge" rule also touches enums: this file regenerates
every real enum category (not just `BlendMode`) with a new nominal identity,
because Luau has no way to add one key to Roblox's own `Enum` table without
redeclaring the whole thing. Ordinary property assignment and comparison
(`frame.BackgroundTransparency`, `if x == Enum.Font.SourceSans`) are
unaffected, but a call like `Font.fromEnum(Enum.Font.SourceSans)` -- passing
an `Enum.X` value into a function Roblox's own defs still declare -- can show
a spurious `Expected this to be 'Enum.Font' from '@roblox', but got
'Enum.Font' from '@roblox2'` error. Same root cause, same tradeoff, no
separate fix needed.

## Pull requests

**One observable goal per branch**, and the prefix says which kind of work it
is. A branch that needs "and" to describe it is two branches.

**`main` is always green.** Every commit on it compiles, passes its checks, and
runs.

## Releases

A release is a tag on `main`, not a branch. Tagging a commit `v0.1.0` (`v`
plus whatever `host/Cargo.toml`'s `version` field reads at that commit)
triggers a workflow that builds `dew.exe` in release mode on Windows and
attaches it to a GitHub Release for that tag. Cutting a release means
bumping `host/Cargo.toml`'s version in an ordinary pull request first, then
tagging the resulting commit once it lands: the release workflow checks the
tag's version against `host/Cargo.toml` and refuses to build if they
disagree, so a shipped `dew.exe`'s own `--version` output always matches the
tag it was published under.

There is no `release/x.y` branch maintained alongside ongoing work on
`main`. The one case that branch is for is reactive: hotfixing something
already shipped after `main` has moved past it. Cut it from the tag at the
moment the fix is actually needed, land the fix there, tag the result, and
let the branch end its life once that ships. It is never created ahead of
a release that has not happened yet.
